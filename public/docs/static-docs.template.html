Your first integration

1

Register your application

Register a client with your Tally license number. Your client ID, and application API key are sent by email.

2

Connect TallyPrime

Set up the desktop Connector on the Tally computer using the instructions in your registration email. Configure Tally and open the company you want to sync.

3

Send an authenticated request

Send your client ID and application key in the headers. Start with a ledger statement after the Connector completes its initial sync.

Examples use demo values. Replace company, ledger, stock item, and voucher references with the exact names in your Tally company.

Access

Authentication

Use your client ID and application API key for authenticated requests.

Application / CRM

Client API key

Send both headers on every client endpoint:

X-Client-ID
Client ID from the registration email.
X-API-Key
Your application API key. No additional API secret or Bearer token is required.
Public endpoints

No credentials required

POST /api/v1/clients/register registers your application, and GET /health checks API server availability. Both endpoints can be called without authentication headers.

Registration sends your credentials to the submitted email address. Keep those credentials for authenticated application requests.

Keep your API key on your application server

Use environment variables for credentials. Code examples contain placeholders; API credentials are never entered into this documentation page. Registration and health checks are public.

Integration behavior

Requests, results & retries

Your application calls the cloud API. The desktop Connector communicates with TallyPrime on the customer’s computer.

Your application→Flowups API→Desktop Connector→TallyPrime

Push requests wait for Tally

The six voucher and order push endpoints return 200 after Tally accepts the transaction, 502 if Tally rejects it, or 504 if the wait expires. The default wait is 120 seconds.

Jobs progress through queued, fetching, building_xml, pushing, then succeeded or failed.

A timeout can leave work in progress

Use the returned request_id to read the matching status endpoint before submitting again. Sales Order and ledger status URLs end in /status; other voucher status URLs use the request ID directly.

Reuse an idempotency_key only for the same transaction. A duplicate returns the saved job; it does not replace the payload or restart a failed import.

Company selection
For imports, the company configured in the Connector takes precedence over destination.company. Direct lookups and ledger statements honor an explicit company.
Order due dates
Sales Orders and Purchase Orders need an order_due_date on the order or every item, using a real YYYY-MM-DD date. Purchase Order order_number is a separate supplier-facing reference.
Voucher numbering
A successful push may return voucher_number: null if the assigned Tally number could not be confirmed. submitted_voucher_number records the caller’s reference.
Connector availability
Live pushes and voucher lookups require a responsive Connector and Tally. Saved status records and completed invoice PDFs can be read without a live Tally connection.

Ledger statements use the synced cache

The Connector must remain running and have a completed company snapshot. Tally can be offline after that sync. Inspect last_synced_at, sync_status, and is_stale before relying on freshness. An uninitialized snapshot returns 503. The default ledger response wait is 15 seconds.

Documents

Two PDF flows

Sales invoice

Export the invoice printed by Tally

Call GET /api/v1/sales/pdf with company, ledger, and voucher number, or GET /api/v1/sales/{requestId}/pdf for a successful Sales import.

202 means the PDF is being prepared. Poll the same URL until 200 returns application/pdf. A failed export returns 424; correct the problem and use retry=true for another attempt.

Ledger statement

Generate a report from the synced data

Call POST /api/v1/ledgers/statement/pdf with the same body as the JSON statement, or add ?format=pdf to the JSON statement URL.

Use report_format: "detailed" for item and bill details available in the cache. Individual display flags use strings "yes" or "no". These flags control PDF presentation.

Check the HTTP status and Content-Type before saving a PDF. Errors and pending exports return JSON. In JavaScript use a Blob or ArrayBuffer for a successful PDF response; in Python use response.content.

Troubleshooting

Responses & errors

Most JSON responses include success, code, type, and message. Voucher fields are at the top level. Ledger statement JSON places the report inside data; ledger status places it inside statement.

200 / 201
Successful request / client registered.
202
Invoice PDF pending. Poll the same PDF URL.
400 / 401
Invalid fields / missing or invalid credentials.
404 / 409
Record or voucher not found / conflict, duplicate license, ambiguous lookup, or PDF source not ready.
424 / 429
Tally PDF export failed / registration rate limit reached.
502 / 503 / 504
Tally rejected work or upstream failed / service, Connector, or cache unavailable / response or connection check timed out.
Validation error · HTTP 400
              
                {
                  "success": false,
                  "code": 2001,
                  "type": "BAD_REQUEST",
                  "message": "Invalid sales order request.",
                  "errors": [
                    {
                      "field": "sales_order.items[0].order_due_date",
                      "message": "order_due_date is required on the item or order header."
                    }
                  ]
                }
Illustrative error shape. Actual field paths and messages identify the failing field.

Connection errors may include CONNECTOR_NOT_CONNECTED, CONNECTOR_NOT_RESPONDING, TALLY_NOT_CONNECTED, TALLY_TIMEOUT, or CONNECTOR_CHECK_TIMEOUT. Follow the endpoint’s status and message when deciding whether to retry.
